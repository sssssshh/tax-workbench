# Tax Workbench

세무사의 **고밀도 업무 처리**를 위한 워크벤치입니다.  
3월 신고 시즌처럼 한 명이 수십~수백 개 고객사를 동시에 관리하는 상황을 가정해, **대량 데이터 처리**, **동시 수정 정합성**, **인라인 편집 UX**, **필드 단위 감사 이력**을 중심으로 설계했습니다.

---

## 1. Overview

이 프로젝트는 다음 문제를 해결하기 위해 만들었습니다.

- 고객사 속성(`tier`, `type`)에 따라 업무 생성 규칙이 달라지는 복합 도메인
- 한 화면에서 빠르게 조회/정렬/필터/수정해야 하는 실무형 대시보드
- 여러 담당자가 동시에 수정할 때도 데이터 정합성을 유지해야 하는 환경
- 수천 건 Bulk Insert, 수만 건 CSV Export, 장기 운영 시 10만 건 이상 데이터셋
- “누가 언제 어떤 필드를 어떻게 바꿨는지”를 필드 단위로 추적해야 하는 감사 요구

현재 구현은 과제 범위 안에서 **실행 가능한 프로토타입**에 초점을 맞췄고, README에는 함께 **프로덕션 확장 전략**도 정리했습니다.

## 3. How to Run

### 3.1 Prerequisites
다음 버전이 설치되어 있어야 합니다.

- Java 21
- Node.js 20+ 권장
- npm 10+ 권장

---

### 3.2 Backend 실행

```bash
cd api
./gradlew bootRun
```

Windows:

```bash
cd api
gradlew.bat bootRun
```

기본 실행 주소:

- API: `http://localhost:8080`

현재 저장소 설정 기준으로는 별도 환경 변수 없이 실행 가능하도록 구성했습니다.  
DB는 H2를 사용하며, 개발/과제 실행 기준으로는 **임베디드 환경에서 빠르게 부팅 가능한 구성을 우선**했습니다.

---

### 3.3 Frontend 실행

```bash
cd web
npm install
npm run dev
```

기본 실행 주소:

- Web: `http://localhost:5173`

프론트엔드는 `http://localhost:8080`을 백엔드 기본 주소로 사용합니다.

---

### 3.4 Build

#### Backend
```bash
cd api
./gradlew build
```

#### Frontend
```bash
cd web
npm install

```

실제 기술 구현을 담습니다.

- JPA Entity / Repository 구현체
- Specification 기반 조회
- CSV Exporter
- Audit Event Listener

#### `interfaces`
HTTP API, 요청/응답 DTO, 예외 응답, CORS 설정 등 외부 진입점을 담당합니다.

## 6. Architectural Rationale

### 6.1 왜 계층을 분리했는가
과제의 핵심은 단순 CRUD가 아니라 아래 문제를 동시에 풀어야 하는 점이었습니다.

- 도메인 규칙이 존재함
- 조회/수정/이력/스트리밍이 서로 다른 관심사임
- 기술 스택이 바뀌어도 비즈니스 로직이 쉽게 무너지면 안 됨

그래서 구조를 다음처럼 나눴습니다.

- **도메인**: “무엇이 비즈니스 규칙인가”
- **애플리케이션**: “그 규칙을 어떤 시나리오에서 어떻게 실행하는가”
- **인프라**: “JPA, HTTP, CSV, 이벤트 같은 기술 세부사항”
- **인터페이스**: “외부 요청을 어떤 형식으로 받는가”

이 분리는 과제의 “지속 가능성(Sustainability)” 요구에 대응하기 위한 선택입니다.

---

### 6.2 WorkItem과 Client를 왜 분리했는가
과제에서 `WorkItem`은 독립 엔티티가 아니라 **특정 Client에 귀속**되고, Client의 `tier`, `type`이 WorkItem 생성 로직에 영향을 줍니다.

따라서 모델을 한 테이블의 단순 컬럼 묶음으로 다루기보다:

- `Client`: 고객의 속성과 상태를 표현
- `WorkItem`: 실제 실무 단위의 작업과 라이프사이클을 표현

으로 분리했습니다.

이렇게 하면 고객 정책이 바뀌거나, 고객 속성 변화가 업무 생성 규칙에 미치는 영향이 커져도 도메인 모델을 확장하기가 쉽습니다.

---

### 6.3 도메인 규칙을 WorkItem 생성 시점에 둔 이유
현재 구현은 예를 들어 아래와 같은 규칙을 생성 시점에서 검증합니다.

- VIP 고객에게는 특정 유형의 업무를 제한
- 개인/법인 구분에 따라 허용 가능한 업무 유형 차등 적용

즉, “그냥 DB에 넣고 나중에 막는” 방식이 아니라 **도메인 생성 시점에 잘못된 상태를 미리 차단**하는 접근을 택했습니다.  
이 방식은 예외 처리가 단순해지고, 데이터 정합성이 더 잘 유지됩니다.

---

### 6.4 조회와 쓰기를 분리한 이유
목록 조회는 다음 요구를 만족해야 합니다.

- 필터링
- 정렬
- 페이징
- 나중에 10만 건 이상으로 확장 가능해야 함

반면 쓰기 로직은 다음 요구가 중요합니다.

- 도메인 규칙 적용
- 동시성 제어
- 변경 이력 기록

그래서 목록 조회는 `Specification` 기반으로, 쓰기 쪽은 유스케이스와 도메인 객체를 통해 관리했습니다.  
읽기와 쓰기의 요구가 서로 다르기 때문에, 같은 코드에 모두 몰아넣지 않는 편이 유지보수성이 높다고 판단했습니다.

---

### 6.5 감사 이력을 이벤트로 분리한 이유
업무 수정 시 감사 로그를 같은 흐름 안에서 동기적으로 모두 처리하면, 수정 핫패스가 무거워집니다.  
그래서 현재 구현은 **업무 수정 이벤트**를 발행하고, 별도의 리스너에서 감사 이력을 저장하는 방향을 택했습니다.

현재 구현은 과제 범위 내에서 다음 균형을 목표로 했습니다.

- 목록/수정 UX는 빠르게
- 감사 이력은 필드 단위로 남기기
- 이후 별도 저장소/메시지 버스로 확장 가능하도록 구조를 분리

---

### 6.6 프론트엔드를 워크벤치 중심으로 설계한 이유
일반 폼 중심 앱이 아니라 “실무자가 표를 빠르게 훑고 수정하는 화면”이 핵심이라서 다음 방향을 택했습니다.

- 인라인 편집
- 키보드 내비게이션
- 가상 스크롤
- 충돌 모달
- 필터/정렬/페이징을 한 화면에 배치

즉, 프론트도 단순 CRUD 폼이 아니라 **대시보드형 작업 환경**으로 보고 설계했습니다.

---

## 7. Domain Rules

현재 구현의 핵심 규칙은 다음과 같습니다.

### 7.1 Client 속성에 따른 WorkItem 생성 제한
- `Client.tier`
- `Client.type`

을 참조해 업무 유형 허용 범위를 달리합니다.

이 규칙은 “고객이 어떤 특성을 가진 존재인가”와 “어떤 작업이 허용되는가”가 연결되어 있다는 점을 코드로 표현한 것입니다.

### 7.2 WorkItem 상태 변경 규칙
예를 들어 완료된 업무를 무조건 초기 상태로 되돌리는 것은 허용하지 않는 등, 상태 전이 자체를 도메인 메서드에서 관리합니다.

이렇게 하면 컨트롤러나 프론트에서 잘못된 상태 조작을 시도하더라도, 최종 방어선이 도메인에 남습니다.

## 8. Concurrency Strategy

### 8.1 선택: Optimistic Locking
동시 수정이 빈번하더라도, 대부분의 사용자는 서로 다른 항목을 다루는 경우가 많기 때문에 비관적 락보다 **낙관적 락**이 더 적합하다고 판단했습니다.

적용 이유:

- 테이블/행 잠금 비용이 낮음
- 일반 조회 성능에 유리
- 충돌이 발생한 경우에만 비용을 지불
- 워크벤치 UI에서 충돌 해결 UX와 결합하기 쉬움

### 8.2 동작 방식
- `WorkItem`에는 version 필드가 존재
- 프론트는 수정 시 현재 version을 함께 보냄
- 백엔드는 업데이트 시 version 기준으로 충돌을 감지
- 충돌 시 409 응답과 최신 데이터 반환
- 프론트는 충돌 모달에서 사용자에게 선택권 제공

### 8.3 UX 관점 해석
동시성 문제는 백엔드에서 막는 것만으로 끝나지 않습니다.  
사용자는 “왜 저장이 안 되었는지”, “내 값과 서버 값이 어떻게 다른지”를 이해할 수 있어야 합니다.

그래서 충돌은 단순 실패가 아니라:

- 비교 가능한 상태로 보여주고
- 최신 값을 기준으로 다시 적용할 수 있게 하는 UX를 지향했습니다.

## 9. Scalability Strategy

### 9.1 Listing
현재 목록 조회는 다음을 전제로 설계했습니다.

- 서버 사이드 필터링
- 서버 사이드 정렬
- 페이지네이션
- 프론트 가상 스크롤

즉, “모든 데이터를 프론트로 다 가져와서 처리”하지 않고, **서버와 프론트가 역할을 나누는 구조**입니다.

### 9.2 Bulk Insert
과제 범위에서는 API 기반 다건 저장을 지원합니다.  
다만 프로덕션 환경에서는 다음으로 확장하는 것이 적절합니다.

- 업로드 파일 저장
- 파싱 작업 비동기화
- Queue 기반 워커 처리
- 성공/실패 레코드 분리 리포팅
- 재처리 가능 구조

### 9.3 Export
현재는 `StreamingResponseBody` 기반으로 CSV를 스트리밍합니다.

장점:
- 큰 결과를 한 번에 메모리에 올리지 않음
- 사용자 입장에서 즉시 다운로드 가능

프로덕션 확장:
- Export 요청을 Job으로 등록
- 백그라운드 워커가 생성
- 결과 파일을 Blob Storage에 저장
- 만료되는 서명 URL로 제공

이 구조가 더 안전하고 운영 친화적입니다.

## 10. Auditing Strategy

### 10.1 현재 구현
- WorkItem 수정 시 변경 필드를 계산
- 변경 이벤트 발행
- 이벤트 리스너가 필드 단위 감사 로그 저장
- UI에서 업무별 변경 이력 조회 제공

### 10.2 왜 필드 단위인가
실무에서는 “업무가 바뀌었다”보다 “**상태가 언제 바뀌었는지, 담당자가 누구에서 누구로 바뀌었는지**”가 중요합니다.  
그래서 row snapshot보다 **field-level audit**이 더 실용적이라고 판단했습니다.

### 10.3 프로덕션 확장 전략
과제 문서의 “수백만 건 감사 이력” 요구를 진지하게 해석하면, 장기적으로는 다음 전략이 필요합니다.

- Outbox Pattern
- Message Broker / Service Bus
- Audit write store 분리
- 파티셔닝
- 조회용 인덱스 최적화
- 장기 보관 데이터의 cold storage 분리

현재 구현은 이 방향으로 발전시키기 쉬운 **구조적 출발점**으로 설계했습니다.

## 11. Frontend Architecture & UX

### 11.1 상태 관리
- 서버 상태: TanStack Query
- 화면 지역 상태: React `useState`
- 편집/포커스 흐름: 커스텀 훅 + 컴포넌트 로컬 상태

서버 데이터 캐싱과 화면 제어 로직을 분리해, 프론트가 과하게 복잡해지지 않도록 했습니다.

### 11.2 컴포넌트 구성
- `WorkbenchPage`: 화면 조합
- `FilterBar`: 필터/Export
- `WorkbenchTable`: 테이블, 정렬, 편집, 충돌 처리
- `InlineEditor`: 셀 편집
- `BulkCreateModal`: 대량 등록
- `ConflictModal`: 동시성 충돌 UX
- `AuditPage`: 이력 조회

### 11.3 키보드 중심 UX
실무 사용자는 반복적으로 같은 작업을 빠르게 처리해야 하므로, 마우스 클릭 수를 줄이는 방향이 중요했습니다.  
그래서 단순 표 렌더링보다 **워크벤치형 조작 흐름**에 더 비중을 두었습니다.

### 11.4 Virtualization
프론트에서 보이는 행에만 렌더링 비용을 집중해 스크롤 성능을 높였습니다.  
현재 페이지 단위에서의 가상화이지만, 이후 infinite scroll / cursor pagination 구조로도 확장할 수 있습니다.

## 12. Trade-off Analysis

### 12.1 Layered + Domain 분리의 장단점
장점:
- 비즈니스 규칙 위치가 명확해짐
- 기술 변경에 덜 흔들림
- 테스트와 유지보수에 유리

단점:
- 작은 프로젝트 기준으로 파일 수가 늘어남
- 단순 CRUD처럼 보일 수 있는 기능도 구조가 무거워짐

이 과제는 단순 CRUD보다 **설계 철학과 지속 가능성**이 중요한 문제이기 때문에, 복잡도를 감수할 가치가 있다고 판단했습니다.

---

### 12.2 Optimistic Locking의 장단점
장점:
- 일반 조회/수정 흐름에 유리
- 비관적 락보다 운영 비용이 낮음
- UI 기반 충돌 해결과 잘 맞음

단점:
- 충돌 UX를 별도로 설계해야 함
- 사용자가 재적용 과정을 이해해야 함

즉, 락 전략만으로 끝나는 문제가 아니라 **백엔드와 프론트 UX를 같이 설계해야 하는 선택**입니다.

---

### 12.3 CSV Streaming의 장단점
장점:
- 큰 결과를 메모리에 다 올리지 않음
- 구현 난이도 대비 효과가 큼

단점:
- 필터/정렬과 완전히 동일한 조건 정합성을 맞추는 데 주의가 필요함
- 아주 큰 결과에서는 비동기 Job 방식보다 운영 안정성이 떨어질 수 있음

과제 범위에서는 streaming이 현실적인 선택이고, 프로덕션에서는 async export가 더 적합하다고 보았습니다.

---

### 12.4 Audit 이벤트 분리의 장단점
장점:
- 수정 핫패스를 가볍게 유지할 수 있음
- 감사 기능을 별도 관심사로 분리 가능
- 이후 메시지 브로커/비동기 구조로 확장 쉬움

단점:
- 구조 이해 비용이 늘어남
- eventual consistency를 고려해야 할 수 있음

---

### 12.5 문자열 기반 tags 저장의 장단점
장점:
- 구현이 단순함
- 과제 범위에서 빠르게 동작하는 버전을 만들기 좋음

단점:
- 태그 검색/정규화/집계 요구가 커지면 확장성이 약함
- 나중에는 별도 태그 테이블 또는 JSON 컬럼 전략이 더 적합할 수 있음

## 13. Cloud & PaaS Strategy

실제 운영 환경에서는 과제 수준의 단일 애플리케이션을 다음처럼 확장하는 전략을 고려합니다.

### 13.1 앱 배포
- Backend: Azure Container Apps 또는 Azure App Service
- Frontend: Azure Static Web Apps 또는 CDN + Blob Hosting

### 13.2 데이터 저장소
- 개발: H2
- 운영: Azure Database for PostgreSQL

운영 DB에서는 다음이 중요합니다.

- WorkItem 필터 컬럼 인덱스
- Audit 조회 인덱스
- Export/Bulk 작업과 일반 트랜잭션 부하 분리
- 장기 데이터에 대한 파티셔닝 전략

### 13.3 Bulk Insert 고도화
- 업로드 파일은 Blob Storage에 저장
- 업로드 요청은 메타데이터만 기록
- Service Bus에 작업 발행
- Worker가 비동기 처리
- 결과는 성공/실패 행 단위 리포트로 제공

### 13.4 Export 고도화
- 사용자가 Export 요청
- 요청은 Job으로 등록
- 백그라운드 워커가 필터 조건으로 결과 생성
- 생성된 CSV를 Blob Storage에 저장
- 다운로드 URL만 사용자에게 제공

이 방식은 긴 요청으로 인해 API 인스턴스가 오래 점유되는 문제를 줄여줍니다.

### 13.5 Audit 고도화
- Outbox + Event Bus
- 별도 Audit Store
- 기간별 파티션
- 조회 빈도 높은 최근 구간만 핫 스토리지 유지
- 장기 데이터는 cold storage로 이관

### 13.6 캐시/검색
규모가 더 커지면 다음도 고려합니다.

- 조회 필터 캐싱
- 검색 인덱스 분리
- Elastic / OpenSearch 계열 연계
- 담당자/상태/마감일 기준의 고빈도 질의 최적화

## 16. AI Collaboration Reflection

이번 과제에서는 AI를 **코드 생성기**가 아니라 **설계 리뷰어이자 초안 생성 도구**로 활용했습니다.

AI 활용 방식:
- 초기에 레이어 구조, DTO, 리포지토리, 화면 구성의 초안을 빠르게 생성
- 중간에는 동시성 처리, Export 정합성, Audit 구조, README 서술 항목을 점검하는 데 활용
- 후반에는 코드 리뷰 관점에서 누락 사항과 보완 포인트를 체크하는 데 활용

중요하게 본 점은, AI가 제안한 구조를 그대로 채택하지 않고 아래를 직접 판단한 것입니다.

- 어떤 규칙을 도메인에 둘지
- 어떤 책임을 유스케이스에 둘지
- 동시성 문제를 UI/백엔드 양쪽에서 어떻게 다룰지
- 스트리밍/감사/확장 전략을 어디까지 현재 구현에 반영할지
- 과제 범위와 프로덕션 확장 전략을 어떻게 구분할지

AI의 한계도 분명했습니다.

- 표준적인 CRUD 구조를 과도하게 선호하는 경향
- 실제 과제 요구의 뉘앙스보다 “돌아가는 코드” 쪽으로 수렴하는 경향
- 동시성/감사/스트리밍처럼 운영 맥락이 필요한 문제에서는 설계 깊이가 부족할 수 있음

그래서 최종적으로는 AI 초안을 기반으로 하되, **문제 정의와 우선순위는 사람이 주도**하고, AI는 검토와 가속 도구로 사용하는 방식이 가장 효과적이었습니다.
